Why Connect Four?

Two-player, deterministic, turn-taking, zero-sum, perfect information: the textbook setting for adversarial search.

≤ 7
branching factor: one move per non-full column
42
plies at most: the board has 42 cells
742 ≈ 3×1035
loose bound on the size of the game tree
4,531,985,219,092
distinct legal positions, about 4.5×1012 (Edelkamp & Kissmann 2008)
Solved
first player wins by starting in the center column (Allen and, independently, Allis, 1988)

{{ icon('info', 22) }}Far too many positions to enumerate in Python during play, so every searching agent here uses depth-limited search or sampling.

  • Small enough to understand, big enough that brute force is hopeless: about 4.5 trillion legal positions.
  • Branching factor is at most 7 and shrinks as columns fill; a game lasts at most 42 plies.
  • The game is solved: James D. Allen announced a solution on 1 October 1988 and Victor Allis, independently, 15 days later (source: John Tromp's Connect Four page). Perfect play wins for the first player from the center. Our agents do not use that solution; they must search.
{{ kicker(3, 'Problem formulation') }}

Connect Four as a search problem

StateA 6×7 grid, each cell empty, Red or Yellow; stored internally as two 49-bit integers
Initial stateThe empty board. Red moves first.
TO-MOVE(s)Red if the number of discs is even, otherwise Yellow
ACTIONS(s)The columns 0..6 that hold fewer than 6 discs
RESULT(s, a)The mover's disc lands in the lowest empty cell of column a
IS-TERMINAL(s)Four in a row (horizontal, vertical or either diagonal), or all 42 cells full
UTILITY(s, p)Win +1, draw 0, loss −1; in search scaled to ±(1,000,000 − ply) so faster wins and slower losses are preferred
  • This is the AIMA 4th edition Chapter 5 game formulation: initial state S0, TO-MOVE, ACTIONS, RESULT, IS-TERMINAL, UTILITY. (The 3rd edition called TO-MOVE and IS-TERMINAL PLAYER and TERMINAL-TEST.)
  • Gravity makes ACTIONS simple: at most seven columns, and RESULT drops the disc to the lowest empty cell.
  • Subtracting the ply from the win score makes the agent prefer the fastest win and the slowest loss.

{{ kicker(5, 'Algorithm') }}

Minimax: assume the opponent is perfect

  • Back values up the tree: MIN nodes take the minimum, MAX the maximum.
  • Cut off at depth d: proven results get ±(1,000,000 − ply), other leaves the heuristic, unless the side to move can win at once (slide 11).
  • Moves are made and unmade in place on the bitboards: no board is ever copied.
  • From the empty board it visits exactly 1 + 7 + … + 7d nodes (400 at d = 3, checked by a test).

Time O(bd) · Space O(b·d) + leaf memo  ·  Anything beyond depth d is invisible: the horizon effect.

  • Walk the tree: each MIN node takes its smallest leaf (3, 2, 2), so MAX picks the left move worth 3. The highlighted line is the principal variation.
  • The cost is the problem: it visits every one of about bd positions, so plain Minimax is capped at depth 6 in the app.
  • Leaf values are memoised per search; that saves time but does not change the node count. The memo grows with the number of distinct leaves, so memory is O(b·d) for the search plus the memo.

Alpha-beta pruning + move ordering

αthe best value MAX can already guarantee
βthe best value MIN can already guarantee
if α ≥ β: skip the remaining siblings
  • The root value is identical to Minimax at the same depth; tests verify it on 7 positions × 4 depths × both orderings.
  • Best case O(bd/2) with perfect ordering (Knuth & Moore 1975), O(bd) in the worst case.
Center-first ordering
{% set order = {3: 1, 2: 2, 4: 3, 1: 4, 5: 5, 0: 6, 6: 7} %}
{% for c in range(7) %}
{{ order[c] }} col {{ c + 1 }}
{% endfor %}

Tried in the order columns 4, 3, 5, 2, 6, 1, 7 (0-indexed 3, 2, 4, 1, 5, 0, 6). Central columns take part in the most four-in-a-row lines, so good moves come first and cut-offs come sooner.

  • Key point: alpha-beta is not an approximation. It returns the same value as Minimax, it just proves that some branches cannot matter. The chosen column can differ only among equally valued moves, because ties go to whichever move is searched first.
  • Pruning only pays off if good moves are tried first; center-first is a cheap, static ordering that works well for Connect Four.
  • For root moves that fail low the score is an upper bound, not an exact value; that is the nature of alpha-beta.
{{ kicker(7, 'Evaluation') }}

Heuristic: window scoring

All 69 four-cell lines on the board are precomputed as bit masks: 24 horizontal, 21 vertical, 12 per diagonal direction.

{{ window(['R', 'R', 'R', ''], '+5', 'own three + one empty') }} {{ window(['R', 'R', '', ''], '+2', 'own two + two empty') }} {{ window(['R', 'Y', '', ''], '0', 'both colours: can never be four') }} {{ window(['Y', 'Y', '', ''], '−1', 'opponent two + two empty') }} {{ window(['Y', 'Y', 'Y', ''], '−4', 'opponent three: a threat') }}

Plus ±3 for each own / opponent disc in the center column. Scored from Red's view here.

  • Proven wins (±1,000,000 − ply) always dominate: every heuristic score is a small integer.
  • A mild attacking bias (+5 vs −4). The function is static, so search checks a playable four for the side to move itself (slide 11).
  • Cheap: one call is 69 AND-and-popcount operations.
  • Not "admissible": that is an A* idea. AIMA (4th ed. §5.3.1) asks an evaluation to order terminals correctly, be cheap, and correlate with winning.
  • A window that already holds both colours is dead and scores nothing; the function counts only lines that can still become four.
  • The center column gets a bonus because it lies in 51 of the 69 windows, more than any other column (39, 27 and 15 for the columns further out; counted from engine/evaluate.WINDOWS).
  • Be honest about it: the weights are hand-tuned, not learned, and ignore Connect Four's odd/even threat parity. The evaluation does not know whose turn it is; the +5 / −4 asymmetry is just a mild attacking bias, and making it symmetric changed nothing measurable.

{% set visits = [226, 195, 129, 435, 271, 101, 143] %} {% set rates = [46, 44, 38, 53, 49, 34, 40] %}
  • No evaluation function: MCTS learns from the win, loss or draw outcomes of playouts. Its only game knowledge beyond the rules is the rollouts' one-move tactics (next point).
  • The first UCB1 term exploits moves that have done well; the second explores moves tried rarely. c = √2 is the constant of UCB1 (Auer, Cesa-Bianchi & Fischer 2002); we did not tune it for Connect Four.
  • Rollouts are lightly tactical: take an immediate win, otherwise block an immediate loss. That removes a lot of noise cheaply.
  • The chart is real engine output (seed 1, Yellow to move after 4, 4, 3, 5, 5): 435 of 1,500 visits went to column 4, so it plays the "robust child".
{{ kicker(9, 'Engineering') }}

A board is two integers

{% for h in range(6, -1, -1) %} {% for c in range(7) %}{{ c * 7 + h }}{% endfor %} {% endfor %} top row: sentinel, always 0 · highlighted: bits 21 and 22, two discs at the bottom of column 4
movebb[p] |= 1 << heights[c]; heights[c] += 1
win?m = bb & (bb >> s);  m & (m >> 2s) ≠ 0
  • One integer per player, 7 bits per column. Make and undo are O(1), so search never copies a board.
  • Four-in-a-row for shifts s ∈ {1, 7, 8, 6} (vertical, horizontal, both diagonals): eight shift-and-AND operations, no loops over cells.
  • The empty sentinel row stops lines wrapping from one column into the next (test_no_wraparound).
  • This is what makes depth 6 affordable in pure Python: a move is one OR and one increment.
  • Explain the win test: shifting by s and ANDing finds pairs; doing it again by 2s finds four in a row.
  • Credit: two per-player bitboards with 7 bits per column and a heights array is the layout of John Tromp's Fhourstones solver; the whole-board threat check used at the search horizon follows Pascal Pons' solver tutorial.
  • The public API still uses a friendly 6×7 list of lists; Board.from_grid and Board.to_grid convert at the boundary.

Alpha-Beta-6 and MCTS are statistically tied (head-to-head 15–21–4). AB-6 costs about what Minimax-4 does per move and beat it 26–11–3.

python benchmark.py · 40 games per pairing: 20 random 2-ply openings × both colours, seed 0 · Wilson 95% CIs

  • Pruning is where the power comes from: 137,257 nodes down to 1,493 at depth 6, 98.9% fewer for the same root value. Even without ordering, pruning skips 88.2% of the tree (16,183 nodes). Times vary by machine (239 ms to 3.4 ms in this run); node counts do not.
  • Ordering alone gives a further 10.8× (16,183 to 1,493). The Knuth–Moore minimal tree at depth 6 has 1,249 nodes (685 of them leaves), so ordered alpha-beta is within 1.2× of the theoretical best case. In AIMA's definition of the effective branching factor (N + 1 = 1 + b* + … + (b*)d), b* is 7.00 for Minimax, 4.84 unordered, 3.17 ordered, and 3.07 for the minimal tree.
  • Say it plainly: Alpha-Beta-6 (77% [70, 83]) and MCTS-1,500 (76% [69, 82]) are statistically tied; their intervals overlap and MCTS led the head-to-head 21–15–4, which is also within the noise. MCTS needs no evaluation function but spends about ten times longer per move (69 vs 7.2 ms).
  • Design: 20 random 2-ply openings, each played with both colours, because two deterministic agents from the empty board just replay the same one or two games. Greedy still took one game of 40 from Alpha-Beta-6: depth 6 is far short of 42 plies. The intervals are Wilson 95% intervals with a draw counted as half a win; that is an approximation, because a score with draws is not strictly binomial.
{{ kicker(11, 'What we found and fixed') }}

A bug we found: the horizon at odd depths

{# Alpha-Beta's score (%) against MCTS (1,000 iterations), 98 games per depth (benchmark.py depth sweep). #} {% set before = [1, 37, 21, 53, 41, 55, 55] %} {% set after = [19, 41, 43, 52, 52, 61, 58] %}
  • Hypothesis: the evaluation is static. At odd depths the opponent moves next at the leaf, so "opponent wins next move" scored as a mere −4.
  • Measured: 14–18% of pre-fix lines at depths 3, 5 and 7 ended one move before a loss the search could not see.
  • Three fixes tested: side-to-move scoring and symmetric weights changed nothing; a leaf win check did.
  • Chosen, because it is exact: if the side to move can win at once, score the proven result. No extra nodes.
  • Result: depth 3 vs Greedy 65% → 94%; strength now rises with depth.
  • Symptom: depths 3 and 5 played no better than 2 and 4. In the old benchmark Greedy split 20–20 with Alpha-Beta at depths 1, 3 and 5 but lost 0–40 at depths 2 and 4; against MCTS the score dipped from 37% (depth 2) to 21% (depth 3).
  • Our evaluation function is static: it doesn't know whose turn it is. At odd search depths the opponent moves next at the leaf, so a position where the opponent can win on the next move was scored as a mere "opponent three, −4". The agent walked into one-move losses just beyond its horizon.
  • Measurement: on 300 random positions, 41 of 281 principal-variation leaves at depth 3, 48 of 274 at depth 5 and 37 of 267 at depth 7 had an immediate win for the opponent to move.
  • We measured three candidate fixes. Scoring leaves from the side to move's view and making the weights symmetric made no measurable difference. The one that worked, and is exactly correct, is to check at each leaf whether the side to move can win immediately and score that as the proven win or loss it is.
  • It costs a few whole-board bit operations (Pascal Pons' threat trick), no extra nodes; Minimax and Alpha-Beta share it, so their values are still identical. After the fix, depth 3 beats Greedy 94% instead of 65%, and strength rises with depth (neighbouring depths are within the noise).
{{ kicker(12, 'Explainability') }}

Every move comes with a sentence and a tree

Alpha-Beta, depth 6"Alpha-beta with center-first ordering (depth 6, 2,657 positions, 3,088 branches pruned) rates column 4 best with a score of +4; pruning proved no other column scores higher."
MCTS, 1,500 iterations"Most-explored move after 1,500 simulations: column 4 (435 visits, 53% win rate); runner-up column 5 (271 visits, 49%)."
  • Grounded: tactical facts (win, block, double threat, threat) are verified on the bitboards before they are stated.
  • Visible: the search tree (first 3 plies, at most 400 nodes) marks pruned branches and the expected line of play.
  • Honest: every number in the AI Mind panel comes from the real search, and a test checks that tracing never changes the move or the node counts.
  • Why it matters: a black box that says "column 4" teaches nothing. Seeing pruned branches and visit counts makes the algorithms concrete.
  • The explanations are not generated text: they are assembled from checks on the position plus the agent's own search statistics.
  • It also helps debugging: when an agent plays badly, the tree shows whether the heuristic or the horizon misled it.

{{ kicker(14, 'Reflection') }}

Limitations & future work

{{ icon('alert', 22) }} Limitations
  • Python speed: about 0.4M nodes/s for alpha-beta, about 17k tree nodes/s for MCTS (benchmark averages).
  • No transposition table and no iterative deepening; depth is fixed.
  • Static center-first ordering; no killer moves or history heuristic.
  • Hand-tuned heuristic that ignores odd/even threat parity (zugzwang).
  • Plain UCT: no RAVE, no tree reuse, c = √2 not tuned.
{{ icon('sparkles', 22) }} Future work
  • Transposition table keyed by the bitboard pair, plus iterative deepening with a time budget.
  • A perfect-play solver for late positions, to show heuristic vs solved play.
  • Threat-parity features, with weights tuned by self-play or regression.
  • MCTS: tree reuse, RAVE, a tuned c; an "equal time" MCTS vs Alpha-Beta experiment.
  • Elo ratings from larger tournaments.
  • Connect the limitations to the results: the odd-depth weakness turned out to be the static evaluation, not the weights (slide 11). Threat parity is still missing; whether it explains Alpha-Beta-6's one loss to Greedy we have not measured.
  • A compiled engine (C or Rust) would be substantially faster and could search deeper; Python was chosen for clarity. The speeds on the slide are benchmark averages on the development machine: 2,857 nodes in 7.2 ms per Alpha-Beta move, 1,180 tree nodes in 69 ms per MCTS move.
  • Alpha-beta column bars are exact only for the chosen move (others are upper bounds), and 40 games per pairing still gives intervals about ±15 points wide.
